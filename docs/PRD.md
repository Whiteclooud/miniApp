# PRD

## 项目名称

单店美甲预约微信小程序

## 产品目标

为单店美甲店提供一个轻量、可运营的小程序：
- 顾客可查看门店风格与返图案例，并提交预约申请
- 店员可配置可预约规则，并对预约申请进行审核
- 系统围绕“单员工、单门店、预约审批制”打通最小业务闭环

## 为什么现在做

当前门店只有 1 名员工，线下靠人工沟通预约容易出现：
- 时间规则不透明，顾客不知道哪些时间可申请
- 店主需要手工反复确认是否接单
- 缺少统一的案例展示入口，影响转化

因此 V1 优先做：案例展示 + 可配置预约 + 审批通过。

## 最新收口（2026-03-14）

- 前后端接口以 `docs/API.md` 为唯一口径，禁止继续使用旧的 `/api/v1/services` 与旧版预约字段。
- 预约页以“可预约日期 + 时间段”为核心，不再要求先选服务项目。
- 顾客身份主键从“手机号查询”升级为“微信 OpenID 自动识别”，姓名/手机号仅作补充信息。
- 首页与预约流程补充人工测试用例，确保“返图展示可见”不等于“流程已跑通”。

## 目标用户

### 1. 顾客
- 浏览门店信息与返图案例
- 查看可预约日期/时间段
- 提交预约申请
- 查看预约状态

### 2. 店员 / 店主
- 配置预约开放规则
- 设置每月不可预约日期
- 设置提前开放预约天数
- 设置每日可预约时间段
- 审核预约申请（通过 / 拒绝）

## V1 范围

### A. 顾客端
- 首页展示门店介绍、品牌氛围、主 CTA，并提供“顾客入口 / 店员入口”清晰分流
- 展示顾客返图 / 案例内容
- 进入预约页并选择日期、时间段
- 提交预约时以微信身份（OpenID）作为用户唯一标识，表单仅补充姓名/手机号/备注（姓名、手机号可选）
- 查看自己的预约申请状态（待审核 / 已通过 / 已拒绝），按微信身份自动过滤

### B. 店员端
- 配置预约规则：
  - 提前多少天开放预约
  - 每月哪些日期不可预约
  - 每天开放哪些时间段可预约
- 查看预约申请列表
- 审核预约申请：通过 / 拒绝
- 审核后预约状态持久化保存

### C. 预约规则逻辑
- 单员工模式下，同一时间段只能接待 1 个预约
- 顾客只能申请当前规则允许的日期和时间段
- 顾客提交后默认状态为 `pending`
- 只有店员审核通过后才变为正式预约 `approved`

## 核心用户流程

### 顾客预约流程
1. 进入首页
2. 查看门店氛围与返图案例
3. 点击“立即预约”进入预约页
4. 选择可预约日期
5. 选择可预约时间段
6. 填写姓名、手机号、备注
7. 提交预约申请
8. 系统生成 `pending` 状态
9. 店员审核后，顾客在“我的预约”中看到结果

### 店员配置与审核流程
1. 进入店员端规则配置页
2. 设置提前开放预约天数
3. 设置本月不可预约日期
4. 设置每日可预约时间段
5. 保存规则
6. 进入预约审核页查看待处理申请
7. 选择通过或拒绝
8. 系统更新预约状态

## 成功标准

- 顾客可在 3 分钟内完成一次预约申请提交
- 顾客不能提交规则外日期 / 时间段的预约
- 店员可以独立完成预约规则配置，不依赖开发改代码
- 店员可审核预约申请，并使状态正确变更
- 顾客端可看到返图展示内容，且首页不显得过于工具化
- 单员工模式下不会出现同一时间段重复通过的预约

## 当前假设

- 当前只有 1 家门店、1 名员工
- 当前不做员工选择，因为无需多技师分配
- 顾客提交预约后，默认进入待审核，不自动通过
- 顾客身份以微信 OpenID 为准；姓名/手机号仅作为联系补充信息（非主键）
- 返图展示 V1 先支持前台展示，内容先接受后台静态配置或轻量管理维护
- V1 优先采用“顾客端 + 店员端同一小程序”方案，以 `pages/staff/*` 作为店员模式页面，不额外拆独立管理后台
- 预约容量按“每个时间段最多 1 单”处理
- 若预约被拒绝，V1 可选填拒绝原因，不强制要求复杂通知链路

## 店员端与顾客端同端承载方案

### 可行性

可以区分。
V1 可通过“页面入口 + 身份校验 + 接口权限前缀”实现店员与顾客区分：
- 顾客页面：`pages/home`、`pages/booking`、`pages/my-bookings`
- 店员页面：`pages/staff/rules`、`pages/staff/appointments`
- 后端接口：顾客侧 `/api/v1/*`，店员侧 `/api/v1/staff/*`

### 优点

- 开发更快，适合当前单店、单员工场景
- 顾客端与店员端共用一套品牌样式、基础能力和发布流程
- 成本更低，不需要额外维护独立后台项目
- 早期业务变化时，调整速度更快

### 缺点

- 权限边界天然比“独立后台”更脆弱，需要补最小身份校验
- 小程序信息架构会更复杂，需要避免店员页面被普通顾客误触达
- 后续若店员功能越来越多，同端承载会让页面和状态管理变重

### 当前建议

- V1 采用同一小程序承载顾客端与店员端
- 但要在前后端实现中预留后续拆分空间
- 若未来出现多员工、多门店、报表、商品管理等需求，再考虑拆独立后台

## UI / 体验方向

参考站点：`https://maggie-app.com/`

本项目先抽象其气质，而不是逐页照搬：
- 轻盈、温柔、有品牌感
- 大图驱动 + 卡片化信息呈现
- 留白充足、圆角明显、避免后台感过重
- 首页既要有“案例吸引力”，也要有明确预约 CTA

建议视觉关键词：
- 柔和奶白 / 浅粉 / 暖灰配色
- 真实手部 / 美甲成品图片为主视觉
- 标题简洁、按钮明确、表单低打扰
