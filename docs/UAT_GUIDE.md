# UAT Guide

## 文档目标

这份文档用于指导 Lan 在微信开发者工具中完成一轮 **基于 `apps/api` 唯一后端基线的页面级 UAT**。

本轮验收不再围绕旧 `apps/server`、切流或回滚展开，而是确认：

1. **当前唯一主线是否稳定**：`apps/weapp + apps/api`
2. **页面级体验是否与冻结文档一致**：首页返图、顾客预约、店员规则、店员月历、审核回查
3. **旧基线退场后是否仍可继续作为后续维护/演进的稳定起点**

当前项目已经完成：

所以你现在如果要做验收，建议把它理解成：

> **围绕当前唯一主线做一轮真实页面回归验收**

本轮优先关注 6 个页面/链路：

1. 首页返图封面 -> 详情多图
2. 顾客预约页未来日期窗口 + 时段原因展示
3. 我的预约回查

5. 店员月历常驻 + 全量预约聚合
6. 店员审核 / 驳回后，顾客侧结果回查

## 一、验收前准备

### 1. 启动后端

在项目根目录执行：

```bash
npm run dev:api
```

如果你只想按当前配置直接启动，也可以：

```bash
npm run start:api
```

默认接口地址：

```text
http://127.0.0.1:3100
```

> 前提：本地 `apps/api` 所需数据库与 `.env` 已按当前主线配置完成；若你之前已经能正常启动 `apps/api`，继续沿用当前本机环境即可。

### 2. 可选：先跑后端自测

```bash
npm run test:api
```

如果通过，说明 `apps/api` 当前主链路在机器自测层面没有明显回退。

### 3. 打开微信开发者工具

- 打开目录：`apps/weapp`
- 确认开发环境请求基地址为：`http://127.0.0.1:3100`
- 确认当前前端已连接 `apps/api` 主线，而不是历史旧基线

### 4. 准备测试身份

#### 店员 OpenID

本地 UAT 建议使用：

```text
staff-openid-demo
```

#### 顾客 OpenID

开发环境建议使用稳定 mock 值，例如：

```text
customer-openid-demo
```

重点不是具体值，而是确认：
- 顾客请求头使用 `X-Customer-OpenId`
- 店员请求头使用 `X-Staff-OpenId`
- 页面回查与审核链路在同一组身份下可连续复现

## 三、详细验收步骤

## Case 1：首页返图封面 -> 详情多图

### 操作
1. 打开首页 `pages/home`
2. 观察首页返图区是否展示封面卡片
3. 点击任意一条返图卡片，进入 `pages/gallery-detail`

### 预期结果
- 首页展示的是封面图，不直接把全部详情图铺开
- 卡片点击后能进入详情页
- 详情页能展示该案例的多图；若后端该条数据缺少 `imageUrls`，也至少会用封面图兜底
- 页面不白屏，空态/错误态可理解

### 若失败，记录什么
- 是首页不显示、点击无跳转，还是详情页空白
- 当前点击的案例标题
- 截图

---

## Case 2：顾客预约页未来日期窗口 + 时段说明

### 操作
1. 进入 `pages/booking`
2. 观察顶部日期条
3. 切换 2~3 个不同日期
4. 观察时间段卡片区
5. 选择一个可预约时间段并提交预约

### 预期结果
- 日期条不只显示“当天”，而是根据 `advanceOpenDays` 展示未来可预约窗口
- 当前选中日期有明显高亮态
- 切换日期会刷新对应时段
- 时间段以卡片/按钮式区域展示，而不是纯文本或下拉框
- 不可预约时段灰显且直接显示原因（如：已约满 / 未开放 / 当日关闭）
- 页面即使只剩 1 个可预约时段，也能通过文案或状态表达让人理解“这是规则/占用结果”，而不是页面坏了
- 提交成功后，生成 `pending` 预约

### 若失败，记录什么
- 选择的日期
- 当前可约/不可约时段表现
- 失败 toast 或报错文案
- 截图

---

## Case 3：顾客查看“我的预约”

### 操作
1. 进入 `pages/my-bookings`
2. 使用与 Case 2 相同的顾客身份刷新页面

### 预期结果
- 能查到刚刚创建的预约
- 状态以中文或明确文案展示，不出现需要人工猜测的原始状态值
- 若已有审核备注 / 驳回原因，可正常展示

### 若失败，记录什么
- 是查不到记录、状态错误还是接口报错
- 当前顾客 OpenID（或 mock 值）
- 截图

---

## Case 4：店员规则结构化配置

### 操作
1. 进入 `pages/staff/rules`
2. 输入店员 OpenID：`staff-openid-demo`
3. 修改并保存：
   - 开放天数
   - 一组闭店日期
   - 2~3 个可预约时间段
4. 保存后重新进入或刷新页面

### 预期结果
- 页面使用结构化控件，而不是要求直接编辑原始文本
- `advanceOpenDays` 有明确选择方式
- `closedDates` 通过日期选择 + 已选列表维护
- `dailySlots` 通过可增删项维护
- 保存成功后，重新进入仍保持刚才的值
- 顾客预约页的日期窗口 / 时段表现会随规则变化而变化

### 若失败，记录什么
- 保存失败还是读回不一致
- 是否出现 401 / 无权限
- 截图

---

## Case 5：店员月历 / 月视图

### 操作
1. 进入 `pages/staff/appointments`
2. 输入店员 OpenID：`staff-openid-demo`
3. 观察页面默认是否显示月历
4. 依次点击：
   - 上月
   - 下月
   - 回到本月
5. 随机点击一个日期

### 预期结果
- 即使没有待审核预约，月历也默认常驻显示
- 可切换月份
- 日期格可看到预约数量、状态标记或摘要信息
- 点击某一天后，下方明细会联动到该日数据
- 月历数据不只覆盖 `pending`，也能体现已通过 / 已拒绝 / 历史预约

### 若失败，记录什么
- 是月历缺失、切月失败还是日期点击不联动
- 当前月份
- 截图

---

## Case 6：店员审核 / 驳回预约

### 操作
1. 在 `pages/staff/appointments` 中找到一条待审核预约
2. 执行一次“通过”
3. 再准备一条待审核预约，执行一次“拒绝”
4. 驳回时可选填写 `reviewNote`

### 预期结果
- 审核通过后，该记录状态更新为 `approved`
- 审核拒绝后，该记录状态更新为 `rejected`
- 若填写 `reviewNote`，顾客侧后续可见
- 对已审核记录再次审核时，页面应给出明确失败提示，而不是静默异常

### 若失败，记录什么
- 是审核按钮无效、接口错误，还是状态不刷新
- 是否出现 `SLOT_OCCUPIED` / `APPOINTMENT_ALREADY_REVIEWED` / 无权限等提示
- 截图

## Case 7：顾客查看审核后结果

### 操作
1. 回到 `pages/my-bookings`
2. 使用同一顾客身份刷新页面

### 预期结果
- 已审核记录能看到最新状态
- 若店员填写了驳回理由 / 审核备注，顾客端可以看到
- 顾客无需再依赖手机号作为主查询条件

### 若失败，记录什么
- 当前顾客身份
- 目标预约记录
- 截图

## 四、可选补充验证

## Case 8：无权限店员访问

### 操作
1. 进入 `pages/staff/rules` 或 `pages/staff/appointments`
2. 输入一个不在白名单内的值，例如：`not-allowed-openid`

### 预期结果
- 页面显性提示“当前账号无店员权限”或等价文案
- 不应返回规则数据或预约列表

---

## Case 9：接口口径一致性（防回退）

### 操作
1. 打开微信开发者工具 Network 面板
2. 依次跑：首页 -> 预约 -> 我的预约 -> 店员规则 -> 店员审核

### 预期结果
- 请求主线集中在当前冻结契约：
  - `/api/v1/gallery`
  - `/api/v1/availability`
  - `POST /api/v1/appointments`
  - `GET /api/v1/my/appointments`
  - `/api/v1/staff/*`
- 不应再看到旧基线或历史并行阶段接口
