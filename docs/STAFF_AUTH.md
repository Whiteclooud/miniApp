# STAFF_AUTH

## 目标

为“同一小程序承载顾客端与店员端”的 V1 方案提供最小可行身份校验方案。

要求：
- 不阻塞当前开发
- 能把普通顾客与店员操作区分开
- 后续可平滑升级

---

## 方案 A：店员 OpenID 白名单（推荐）

### 思路
- 小程序登录后获取用户 OpenID
- 后端维护一个店员白名单（当前只有 1 人可极简实现）
- 访问 `/api/v1/staff/*` 时检查该 OpenID 是否在白名单中

### 优点
- 实现轻量
- 边界清晰
- 安全性明显强于“前端隐藏页面”
- 后续可自然扩展到多店员

### 缺点
- 需要接入最小登录识别
- 首次录入店员 OpenID 需要一次人工配置

### 适用性
- 非常适合你当前“单员工、V1 快速上线”的场景

---

## 方案 B：固定 staff 入口 + 后端口令校验

### 思路
- 提供一个受控 staff 页面入口
- 店员进入时输入固定管理口令
- 后端校验通过后发放短期 staff token

### 优点
- 前期实现快
- 无需马上接复杂身份体系

### 缺点
- 口令易泄露
- 安全性一般
- 后续扩展性不如 OpenID 白名单

### 适用性
- 只适合作为非常临时的过渡方案

---

## 方案 C：独立后台 / 独立 staff 小程序

### 思路
- 顾客端与店员端从产品层面彻底拆开

### 优点
- 权限天然更清晰
- 管理端可独立扩展

### 缺点
- 开发、测试、维护成本高
- 不适合当前单员工轻管理场景

### 适用性
- 适合后续扩展到商品、报表、多员工、多门店后再考虑

---

## 推荐结论

### V1 推荐：方案 A
即：
- 同一小程序
- 顾客页与店员页分目录
- 后端 staff 接口独立前缀
- 店员身份采用 OpenID 白名单校验

这是当前“实现成本 / 安全性 / 后续扩展”三者之间最平衡的方案。

---

## V1 最小落地要求

### 前端
- 不在普通 tab 中暴露店员页面
- 店员入口可采用受控跳转
- staff 页面在未授权时给出明确提示
- 所有 staff 请求统一走一个请求封装，不允许每个页面单独拼 header

### 后端
- `/api/v1/staff/*` 必须统一做身份校验
- 不能只靠前端隐藏页面
- 白名单配置应可在环境变量或配置文件中维护
- staff 鉴权失败时统一返回 `401` + `code=STAFF_UNAUTHORIZED`

### 数据
- 白名单至少支持 1 个店员账号
- 后续允许扩展为多个 OpenID

## V1 实施契约（默认按此口径开发）

### 1. 请求头约定
- 体验版 / 正式版：`Authorization: Bearer <token>`，服务端会复核 session、关联用户 `ACTIVE` 状态、当前角色和 `STAFF_OPEN_IDS` 白名单。
- develop 兼容：`X-Staff-OpenId`，仅在请求未提供 Bearer token 时生效。
- 缺失、过期、被撤销、用户被禁用、角色已变更或不在白名单内时：统一返回 `401 + STAFF_UNAUTHORIZED`。

### 2. 白名单配置建议
- 环境变量：`STAFF_OPEN_IDS`
- 格式：逗号分隔，例如：`openid_a,openid_b`
- V1 若暂时只有 1 名店员，也按同一格式保留多值扩展能力

### 3. 前端接入建议
- 建立统一方法，例如 `getStaffHeaders()` 或 staff request wrapper
- 页面层不直接决定 header 内容，只调用统一封装
- 开发联调阶段若登录链路未接完，允许在本地开发配置中临时写死 mock openid；但该兜底仅限开发环境，禁止直接写入生产代码常量

### 4. 后端校验建议
- 在进入具体 staff 路由前统一校验 header
- 失败时返回：

```json
{
  "error": "Staff unauthorized",
  "code": "STAFF_UNAUTHORIZED"
}
```

- 不要在单个 handler 内重复散落鉴权判断

### 5. 未授权用户体验
- 前端收到 `STAFF_UNAUTHORIZED` 后，统一提示“当前账号无店员权限”
- 不暴露调试性错误细节给顾客端
- staff 页面允许保留返回首页或退出入口

## 后续升级路径

### V1 -> V2
- 从单 OpenID 白名单升级为多 staff 管理
- 增加操作日志
- 增加更明确的 staff 角色（owner / assistant）

### V2 -> V3
- 如商品售卖、报表、库存、营销能力变多，再考虑拆独立后台
